1 · وثيقة متطلبات الأعمال (BRD)

تحدّد هذه الوثيقة سبب المشروع ونطاقه وأصحاب مصلحته وقواعد أعماله ومؤشرات نجاحه، وتشكّل المرجع الذي تُبنى عليه بقية الأقسام.

1.1 تعريف المشروع

موقع إلكتروني عربي حديث (RTL) لجمعية حاضنة الجمعيات — وهي جمعية غير ربحية سعودية مقرّها الرياض تُعنى باحتضان الجمعيات وتطوير قدراتها المؤسسية عبر التأسيس والحوكمة وبناء القدرات والاستدامة المالية والتحول الرقمي وقياس الأثر. يهدف المشروع إلى إطلاق واجهة عامة احترافية تعرّف بالجمعية وبرامجها وتقدّم خدمات إلكترونية للجمهور، مصحوبةً بلوحة تحكّم لإدارة المحتوى، مع الإبقاء على الموقع القديم أثناء مرحلة التشغيل التجريبي.

الموقع مبنيّ كصفحات HTML ثابتة ومكتفية ذاتيًا (التنسيق والخطوط والشعار مضمّنة)، ومنشور على Cloudflare Pages، مع مسار مخطّط لإضافة خلفية عبر Workers + D1 لتشغيل النماذج ولوحة التحكّم فعليًا، وتخزين ملفات PDF عبر R2.

نطاق هذه الوثيقة

تُوثّق النظام كـموقع منظمة واحدة (الجمعية) مع لوحة محتوى وخدمات عامة. لا يشمل النطاق منتجًا متعدّد المستأجرين (SaaS)؛ ولذلك كُيّفت الأقسام الموجّهة للمنتجات الجماعية (مثل «إنفاذ الباقات») لتناسب سياق المنظمة الواحدة. يُشار في القسم 14 إلى كيفية تعميم النظام لاحقًا كقالب لجمعيات أخرى.

1.4 النطاق

داخل النطاق:

  • 16 صفحة عامة: الرئيسية، من نحن، البرامج، الأخبار، الحوكمة، تواصل، مجلس الإدارة، اللجان، فريق العمل، الجمعية العمومية، الأوقاف والاستثمارات، التراخيص، تطوّع، العضوية، الوظائف، قياس الرضا.
  • لوحة تحكّم / CMS (نموذج أولي): الثيم والهوية، المحتوى والأقسام، القوائم، الأخبار، الإعدادات، الأكواد المخصّصة لكل صفحة، صندوق الطلبات، والمستخدمون والصلاحيات.
  • نماذج الخدمات العامة: تطوّع، عضوية، توظيف، واستبيانات قياس الرضا.
  • مكتبة ملفات PDF للحوكمة والتراخيص مع روابط تحميل.
  • تهيئة الظهور: وسوم SEO وOpen Graph، وخريطة الموقع sitemap.xml، وrobots.txt، وصفحة 404، وأيقونة الموقع.
  • النشر على Cloudflare Pages عبر نطاق فرعي تجريبي ثم النطاق الرسمي.
  • لاحقًا: خلفية Workers + D1 للنماذج والمصادقة، وتخزين الملفات على R2، وتفعيل تحليلات الزيارات.

خارج النطاق (حاليًا):

  • بوابة دفع أو تبرّعات مدمجة، ونظام إدارة تعلّم (LMS)، وتطبيق جوال.
  • تعدّد المستأجرين (SaaS) وتعميم المنصّة لعدة جمعيات في هذه المرحلة.
  • المراسلات البريدية الآلية والبريد الرسمي باسم النطاق.
  • لوحة مصادقة إنتاجية كاملة (مؤجّلة إلى مرحلة الخلفية).
  • التكامل المباشر مع الأنظمة الحكومية.

1.7 الافتراضات

  • الإدارة التقنية على عاتق فريق بسيط، فتُفضّل الحلول المُدارة قليلة الصيانة.

3.3 حالات استخدام مفصّلة

UC-03 تقديم طلب تطوّع

الفاعل: المتطوّع (زائر).

المسبقات: صفحة «تطوّع معنا» متاحة.

التدفّق الأساسي: يفتح الصفحة ← يملأ الاسم والبريد والجوال والمجال وساعات التفرّغ ← يرسل ← يجري التحقّق من الحقول ← تظهر رسالة نجاح ويُسجَّل الطلب بحالة «جديد».

الاستثناءات: حقول ناقصة أو بريد غير صحيح ← رسائل تحقّق فورية؛ فشل الإرسال ← إتاحة إعادة المحاولة.

ما بعد الشرط: ظهور الطلب في صندوق الوارد (يتطلب الخلفية — BR-06؛ النموذج الأولي يعرض النجاح دون حفظ فعلي).

UC-09 تحرير محتوى صفحة ونشره

الفاعل: محرّر المحتوى.

المسبقات: تسجيل دخول ناجح وصلاحية تحرير المحتوى.

التدفّق الأساسي: يفتح اللوحة ← يختار القسم/الصفحة ← يعدّل النص أو الثيم ← يحفظ ← (اعتماد المدير التنفيذي) ← يُنشر التغيير لكل الزوّار.

الاستثناءات: صلاحية غير كافية ← رفض؛ تعارض تعديلات ← تُعتمد آخر نسخة.

ما بعد الشرط: نشر عام للتعديل (يتطلب نقل التخزين من localStorage إلى الخلفية — BR-06).

UC-12 معالجة طلب في صندوق الوارد

8.4 حماية النماذج العامة

  • التحقّق من الحقول داخل Worker ولا يُعتمد على الواجهة فقط.
  • تحديد المعدّل (rate limiting) ومنع الإرسال المكرّر والإغراق.
  • حماية اختيارية من الروبوتات عبر Cloudflare Turnstile.
  • تعقيم المدخلات ومنع الحقن، والاعتماد على استعلامات معلَّمة (parameterized).
  • تقييد CORS على نطاق الموقع فقط.
  • استبيان الرضا مجهول: لا يُخزَّن معرّف شخصي أو IP مع الرد (R-08، BR-09).

9.2 جسر الإعدادات الحالي

تعمل اللوحة حاليًا عبر مفتاح localStorage باسم aiSiteConfigV2 يُقرأ في كل صفحة ويطبّق: الثيم (متغيّرات CSS)، والهوية، والقوائم، وإظهار الأقسام ونصوصها، وترويسة البطل، وتذييل التواصل، والأكواد المخصّصة لكل صفحة، مع تصدير/استيراد الإعدادات بصيغة JSON.

القيد الحالي

الجسر محلّي على متصفح المحرّر فقط، فلا تظهر التعديلات لبقية الزوّار. يتطلب النشر العام نقل التخزين إلى الخلفية (BR-06).

9.3 نموذج النشر المستهدف

النشر المستهدف: التحرير والاعتماد في اللوحة ← الحفظ في D1/KV ← تقديم Worker ← ظهور التعديل لكل الزوّار.

توصية

نهج هجين: الأخبار والطلبات وإعدادات الموقع تُقرأ وقت التشغيل من KV/D1 (فورية)، والتغييرات النادرة جدًا يمكن دمجها في إعادة نشر مجدولة. إبطال التخزين المؤقت (cache purge) عند كل نشر.

9.5 سير عمل النشر

  • الحالات: مسودة ← مراجعة/اعتماد ← منشور ← تحديث/أرشفة (انظر آلة حالة المحتوى في القسم 5).
  • لا يُنشر للعموم إلا بعد اعتماد المدير التنفيذي (R-02).
  • كل نشر يسجّل مَن ومتى (site_config.updated_by) لأغراض التدقيق.

9.6 استراتيجية الملفات والوسائط

  • الملفات مبدئيًا في /files ضمن النشر، ثم إلى R2 عند التراكم.
  • تسمية الملفات وفق المانيفست وبصيغة PDF (R-04).
  • روابط عامة عبر نطاق R2 مخصّص، مع ترويسات تخزين مؤقت طويلة للأداء.

10 · مسار إرسال النماذج العامة

يوضّح هذا القسم المسار الخادمي لإرسال النماذج العامة عبر Worker على الحافة: التسلسل، وعقد الواجهة، وخطوات المعالجة، ومعالجة الأخطاء، والمسار المجهول للاستبيان.

10.1 مخطّط التسلسل

تسلسل الإرسال: من الزائر عبر صفحة النموذج إلى Worker (تحقّق) ثم D1، والعودة برسالة نجاح.

10.3 خطوات المعالجة الخادمية

  1. التحقّق من الطريقة (POST) وCORS ومصدر الطلب.
  2. تحليل JSON والتحقّق من رمز Turnstile (إن فُعّل).
  3. التحقّق من المخطّط حسب type (حقول كل نموذج).
  4. حدّ المعدّل ومنع التكرار (عبر KV ببصمة IP مؤقتة).
  5. تعقيم المدخلات واستخدام استعلامات معلَّمة.
  6. إدراج السجل في submissions بحالة «جديد» (R-01).
  7. إشعار اختياري للإدارة، ثم إعادة رد النجاح.
